# SnowVision

Оперативная панель наблюдений снегопада в Петропавловске-Камчатском.
Показывает камеры, журнал сигналов, прогноз Яндекс Погоды и штормовой бюллетень.
Требования к [экрану пилота](../context/UI_UX_PILOT_TASK.md) и
[открытые условия](../context/PILOT_NOTES.md) описаны в контексте.

## Запуск и настройки

Нужен Docker Engine с Compose. Команды выполнять из этого каталога.
Локальные переменные хранить в игнорируемом `.env`, образец — [.env.example](.env.example).

```sh
docker compose -p snowvision up --build -d --wait
```

Если настройки уже хранятся в корневом `.env` репозитория, использовать
`docker compose --env-file ../../../.env -p snowvision up --build -d --wait`.
Не копировать ключи в исходники. Вход — http://localhost:5173,
Swagger — http://localhost:5173/docs. Backend наружу не опубликован.
Остановка — `docker compose -p snowvision down` без `-v`: том `history`
содержит историю наблюдений, эпизоды, очередь доставки и последний корректный кадр.
Метаданные наблюдений хранятся семь суток.

| Переменная | Назначение |
| --- | --- |
| `X-Yandex-Weather-Key` | Серверный ключ Яндекс Погоды; без него прогноз имеет статус disabled |
| `SCENE_MODEL_URL` | Необязательный согласованный Weather VLM v2 endpoint с POST /v2/scene |
| `ALERT_WEBHOOK_URL` | Адрес согласованного получателя серверных сигналов |
| `ALERT_WEBHOOK_TOKEN` | Необязательный Bearer-токен получателя |
| `SNOWVISION_PILOT_DIR` | Каталог отдельного архива для профилей quality и quality-model |

## Архитектура

| Каталог | Ответственность |
| --- | --- |
| `backend/snowvision/api` | Маршруты FastAPI и форматы ответов |
| `backend/snowvision/services` | Жизненный цикл, мониторинг и доставка |
| `backend/snowvision/domain` | Анализ кадров, городская агрегация и офлайн-кандидаты |
| `backend/snowvision/adapters` | Источники, прогноз, бюллетень, VLM, SQLite и журнал |
| `backend/snowvision/resources` | Каталоги камер и резервная HTML-страница |
| `backend/snowvision/cli` | Аудит, архивирование и офлайн-оценка |
| `backend/tests` | Тесты backend |
| `frontend/src/app` | Главный экран, состояние и стили |
| `frontend/src/features` | Камеры, сигналы и городская сводка с тестами |

React/TypeScript собирается Vite и обслуживается nginx. Он проксирует `/api`,
Swagger и SSE в FastAPI. Буферизация SSE отключена. Подробности модулей —
[BACKEND.md](../context/BACKEND.md) и [FRONTEND.md](../context/FRONTEND.md).

## Камеры и свежесть

Каталог — `backend/snowvision/resources/cameras.json`; кандидаты и проверки —
`candidates.json` и `source_checks.json` рядом. Для подключения пилотной камеры
проверить городской участок в поле зрения, задать координаты и
`city_observation: true`. Разрешение внешней доставки задаётся отдельно
через `alert_delivery: true`. Для HLS указать `type: hls`.

Временно городской индекс и локальные свидетельства также используют камеры с
координатами при `city_observation: false`; это не подтверждает, что они видят
город. Для возврата проверки поля зрения установите
`SNOWVISION_REQUIRE_VERIFIED_CITY_VIEW=true`. Флаг не меняет допуск к Weather
VLM, onset-сигналам или внешней доставке.

У каждой камеры собственный цикл с блокировкой. Получение ограничено четырьмя
операциями, обработка — двумя. При ошибках действует backoff. Ручное обновление
соблюдает интервал источника и возвращает rate_limited или in_progress.
Для движения нужен пригодный видеоряд минимум из восьми разных кадров с
интервалами до двух секунд. HLS получает серию FFmpeg; редкие JPEG оцениваются
по отдельному снимку. Частота публикации зависит от оператора, для РАН задано
1800 секунд. HTTP 200 и изменение пикселей не доказывают снегопад.

Версия кадра вычисляется по изображению. Неизменившийся JPEG не пополняет
буфер движения и не омолаживает кадр. При сбое сохраняются последний корректный
снимок и его метаданные, оценка становится unknown. Last-Modified и время
получения хранятся раздельно; без метки оператора время съёмки неизвестно.

Frontend использует один EventSource и резервный polling при потере связи.
Изображения подгружаются по видимости с очередью до четырёх загрузок,
таймаутом и backoff. Старый снимок остаётся до декодирования нового.
Отключение автообновления изображений не останавливает backend.

Аудит источников: `docker compose -p snowvision run --rm --no-deps snowvision
python -m snowvision.cli.probe_sources`. Короткая проверка не подтверждает
зависание источника с редкой публикацией; актуальность измерять перед пилотом.

## Городской индекс и сигналы

`GET /api/city/outlook` возвращает индекс, прогноз и бюллетень. Индекс исключает
демо, непроверенные ракурсы, оценки одиночного JPEG, ошибки и устаревшие данные.
Камеры ближе километра объединяются; представитель выбирается по уверенности
и свежести. До двух независимых зон городской индекс отсутствует. Это
инженерное правило, а не доказательство охвата всего города.
Балл OpenCV и уверенность не откалиброваны как вероятность снега.

Численный ответ Gemma с качеством изображения от 0,60 даёт положительное свидетельство при оценке снегопада от 0,70 и отрицательное до 0,30 включительно; остальные случаи неопределённы. Пороги эвристические и не проверены разметкой. События по ним не отправляются во внешнюю доставку. Первое пригодное положительное наблюдение открывает early. Три различные
сильные версии или пригодные положительные ответы VLM дают confirmed.
Повторы версии не подтверждают эпизод. Непригодные данные прерывают набор
подтверждений; три ясных отрицательных наблюдения завершают эпизод.
Принятие оператором хранится отдельно от состояния снегопада.
Демо маркируется и исключается из внешней доставки.

API журнала — `GET /api/alerts`, `POST /api/alerts/{id}/acknowledge`,
`GET /api/monitoring`; SSE передаёт отдельное событие alerts.
Браузерные уведомления включаются пользователем и требуют открытой вкладки.
Webhook работает отдельно от браузера, с очередью SQLite, повторными попытками
и `Idempotency-Key=event_id:stage`. Получатель должен устранять повторы.
Delivered означает HTTP 2xx, а не прочтение диспетчером. При пустом URL доставка
выключена; не отправлять пробные события произвольным адресатам.

Контракт scene в `backend/snowvision/adapters/integrations/team_scene.py`
адаптирован из kamchatka-cam авторства Eazyan. Это самостоятельная копия;
другой checkout не нужен. VLM проверяется по формату, пригодности обзора и
версии кадра. Снег на земле и падающий снег показываются раздельно;
обледенение требует данных состояния покрытия.

## Прогноз и штормовой бюллетень

Яндекс Погода запрашивается сервером для опорной точки района Чехова.
API возвращает текущие данные и почасовой прогноз; frontend показывает до трёх
будущих интервалов. Вероятность относится ко всем осадкам. Устаревшие данные
маркируются, прогноз не меняет стадии сигналов камеры.

Отдельный адаптер получает строку Камчатского края из бюллетеня Росгидромета
по ДФО. Сохраняются источник, время получения, упоминание города и статус даты.
Прошедшие, будущие и неопределённые сроки требуют разных подписей; точное
время проверять по оригиналу. Сохранённый бюллетень при сбое не считается свежим.

## Проверки и дальнейшая работа

```sh
docker compose -p snowvision build web
docker compose -p snowvision exec -T snowvision python -m unittest -v
docker compose -p snowvision exec -T web nginx -t
```

Build web выполняет Vitest, TypeScript и production-сборку. После изменения
backend выполнить `docker compose -p snowvision build snowvision` перед
backend-тестами. CI — `.github/workflows/endermend-ci.yml`.

Профили `quality` и `quality-model` собирают отдельный архив и сравнивают
офлайн-кандидатов. Протокол разметки, критерии допуска и команды — в
[плане качества](../../../task.md). Размеченные городские эпизоды нужны для
измерения точности и задержки; технические тесты их не заменяют.

## Визуальный анализ на компьютере с 8 ГБ RAM

Дополнительные датчики не используются. Снегопад, снег на поверхности и признаки
возможного обледенения оценивает Gemma 3 4B через локальную Ollama.
Модель возвращает четыре численные оценки от 0 до 1 для снега на земле,
снегопада, видимых признаков льда и качества изображения. Они не калиброваны
и не подтверждают сцепление покрытия.
Источник модели: https://ollama.com/library/gemma3:4b ; API: https://docs.ollama.com/api/generate .
Веса хранятся в `SNOWVISION_MODEL_DIR` (по умолчанию
`/mnt/disk_d/Development/kam4atka/snowvision-models`), вне Git.
Память Compose: vision 6 ГБ, backend 1536 МБ, web 256 МБ. Контекст 2048,
одна загруженная модель, один одновременный запрос. Эти лимиты не гарантируют
скорость или точность: CPU и видимость камер требуют фактической проверки.

```sh
docker compose up -d vision
docker compose exec -T vision ollama pull gemma3:4b
docker compose up -d --build --wait
```

При отсутствии весов/ответа модель не выдаёт достоверную погоду. Прогноз и
бюллетень остаются отдельно атрибутированными внешними источниками.
