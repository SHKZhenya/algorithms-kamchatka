# SnowVision Kamchatka

Запуск из этой папки через `docker compose --env-file ../../../.env -p snowvision up --build -d --wait`.
Откройте http://localhost:5173, Swagger доступен по /docs.
Тесты запускаются через `docker compose exec snowvision python -m unittest -v`.

Frontend использует React 19, TypeScript и Vite. Отдельный контейнер nginx
раздаёт production-сборку и проксирует API, Swagger и SSE в FastAPI.
Буферизация SSE отключена. Backend доступен внутри сети Compose,
публичный локальный вход — http://localhost:5173.

Интерфейс включает поиск, фильтры, статусы камер, адаптивные карточки,
диалог с историей и техническими сведениями. Обновления поступают через SSE,
резервный polling и обновление JPEG выполняются каждые десять секунд.
Сводка города учитывает только реальные камеры.

Проверка сборки frontend выполняется при docker compose build web
и включает строгую проверку TypeScript. Зависимости зафиксированы в package-lock.json.
Настройка JPEG-камер находится в cameras.json. Демо создаёт воспроизводимую
последовательность синтетических кадров и всегда помечается как демонстрация.

OpenCV сравнивает 16 последовательных кадров, считает небольшие движущиеся
компоненты и использует медиану их количества. Это некалиброванная эвристическая
оценка, а не статистическая вероятность. Дождь, шум, движение камеры и освещение
могут вызывать ошибки. Низкая частота обновления JPEG ограничивает применимость.
Неизменный более 120 секунд кадр помечается как stale. Время получения HTTP-кадра
не доказывает время съёмки. При ошибке источника оценка становится unknown.

История хранится семь суток в Docker volume. Каждый источник обрабатывается
отдельной задачей, HTTP-параллелизм ограничен четырьмя соединениями.
Поддержка MJPEG/RTSP, повторные попытки внутри одного цикла, полноценная
калибровка и проверка по размеченным реальным видео остаются в работе.

Источники JPEG заимствованы из shared/kamchatka-cam/cameras/sources.json.
Страница оператора https://www.shors.ru/kamery/kamera-shchors.
Географические координаты в интерфейсе не используются.


## Архитектура кода

| Каталог | Ответственность |
| --- | --- |
| `backend/snowvision/api` | Маршруты FastAPI и форматы HTTP-ответов. |
| `backend/snowvision/services` | Жизненный цикл приложения, мониторинг камер и отправка уведомлений. |
| `backend/snowvision/domain` | Анализ кадров и агрегация наблюдений. |
| `backend/snowvision/adapters` | Получение кадров, прогноз, предупреждения, модель, SQLite и журнал сигналов. |
| `backend/snowvision/resources` и `cli` | Каталоги камер, ресурсы HTTP и команды аудита источников. |
| `backend/tests` | Тесты API, мониторинга, анализа и адаптеров. |
| `frontend/src/app` | Экран диспетчера, общее состояние и стили. `frontend/src/main.tsx` монтирует приложение. |
| `frontend/src/features` | Модули камер, оповещений и городской сводки с тестами рядом с компонентами. |

Оба сервиса собираются из собственных каталогов. Запускайте Compose из корня
SnowVision, где находится `compose.yaml`. nginx проксирует `/api` в FastAPI.

При запросе истории `app.py` проверяет идентификатор камеры и вызывает
`observation_store.load_history`. При обновлении камеры `monitor.py` анализирует
кадр и передаёт снимок состояния в `observation_store.save_observation`.
Правила интерпретации кадров остаются в мониторинге и анализе, а формат
HTTP-ответов задаётся в `app.py`. Журнал сигналов и очередь доставки используют
ту же базу, их таблицами управляет `alerts.py`.

## Каталог публичных камер

Проверенные источники находятся в cameras.json. Полный список кандидатов и
результаты получения/декодирования — candidates.json и source_checks.json.
Повторная проверка выполняется через
`docker compose exec -T snowvision python -m snowvision.cli.probe_sources`.

HLS получает один декодированный кадр через FFmpeg с проверкой TLS,
ограниченным временем выполнения и завершением дочернего процесса при отмене.
Число параллельных операций получения ограничено четырьмя. При ошибках
источник повторно проверяется через 30 секунд.

JPEG ЩОРС запрашиваются раз в 30 секунд. Для РАН используется заявленная
оператором частота публикации раз в 30 минут. Для редких JPEG служит оценка
свежего снимка по мелким ярким объектам и их распределению. Карточка
показывает уверенность по кадру. Блики, мелкие детали фона и дождь могут
давать ложные признаки снега.
Last-Modified хранится отдельно от времени получения. Старые файлы отмечаются
как устаревшие. Без метки времени от оператора свежесть съёмки не подтверждается.

Публичные каталоги операторов:
https://kam.emsd.ru/visual-observations/
https://www.shors.ru/kamery/kamera-shchors
https://kam-travel.ru/kamchatka-onlajn/

## Независимые обновления и последний успешный кадр

У каждой камеры один цикл с блокировкой, jitter и интервалом от завершения
попытки. Получение ограничено четырьмя одновременными операциями, обработка
OpenCV и SQLite — двумя. Ошибки используют backoff 30–240 секунд.
`POST /api/cameras/{id}/refresh` выполняет проверку только после истечения
интервала и возвращает `rate_limited` или `in_progress` при ограничении.

Версия кадра вычисляется по декодированному изображению и меняется только при
изменении содержимого. Неизменившийся JPEG не добавляется в буфер движения.
Последний кадр и его метаданные хранятся в SQLite и восстанавливаются после
перезапуска. При ошибке прежние кадр, версия и время кадра сохраняются,
оценка снегопада становится unknown. Время успешного HTTP-получения отделено
от времени последней новой версии и даты файла оператора.

Frontend использует один EventSource и резервный polling только при его
недоступности. IntersectionObserver подгружает изображения за 300 px до
viewport. Одновременно загружается не больше четырёх изображений. Новый JPEG
сначала декодируется, затем заменяет предыдущий с переходом 200 мс.
При выключении автообновления backend продолжает работать. Предпочтение
сохраняется в localStorage. Ручная кнопка проверяет backend и соблюдает его
ограничения. Фильтры и время свежести работают независимо от загрузки JPEG.

Frontend-тесты Vitest/React Testing Library запускаются при сборке образа:

```bash
docker compose build web
docker compose exec -T snowvision python -m unittest discover -v
```

## Городская оценка и прогноз

`GET /api/city/outlook` возвращает индекс наблюдений камер, почасовой прогноз
Яндекс Погоды и штормовые предупреждения Камчатского края. Сервер запрашивает
погоду для опорной точки раз в 10 минут. Один запрос REST `/v2/forecast` с
`limit=2` и `hours=true` даёт наблюдение и прогноз, в том числе после полуночи.
При сетевом тайм-ауте следующая попытка выполняется через минуту.
В панели показываются до трёх ближайших почасовых интервалов с температурой и
типом осадков. Количество, вероятность всех осадков и объём свежего снега
показаны при наличии соответствующих полей. Сохранённый прогноз помечается
устаревшим после 20 минут. Прошедшие интервалы скрываются.

Опорная точка прогноза — приблизительная площадка Чехова, 1А. Численные
координаты взяты из существующей интеграции shared/kamchatka-cam, адрес
подтверждён оператором. Координаты описывают площадку. Географическая область обзора
требует отдельной проверки. Камера image80 имеет уличный ракурс, image96 направлена на
дальние вулканы и исключена из текущего городского индекса.

При агрегации исключаются демо, неподтверждённые городские ракурсы, редкие
снимки, ошибки, устаревшие оценки и уверенность ниже 0.25. Камеры ближе 1 км
объединяются в одну зону, из которой берётся наблюдение с наибольшим весом.
Вес равен confidence × exp(-возраст_анализа/120). Индекс — взвешенное среднее
по зонам. До двух пригодных независимых зон общегородское значение unknown.
Порог 1 км и минимум две зоны — инженерные эвристики, полнота охвата города
ими не подтверждается. Сейчас каталог не обеспечивает такое покрытие.

Документация источника прогноза: [API Яндекс Погоды, REST](https://yandex.ru/dev/weather/doc/ru/concepts/forecast-rest).

## Улучшенная оценка кадров

Медианная фильтрация убирает мелкие частицы перед оценкой движения фона.
Согласованное движение фона проверяется фазовой корреляцией и Lucas–Kanade.
При сдвиге камеры, резкой смене освещения, темноте или низком контрасте
возвращается unknown с диагностической причиной. Для остальных серий
выделяются небольшие яркие движущиеся компоненты. Используются их медианная
плотность, покрытие сетки 4×3 и устойчивость во времени. Крупные объекты и
тонкие длинные компоненты отбрасываются. Признаки качества доступны в
подробностях камеры и в API (`analysis_reason`, `features`).

Для движения снежинок требуется серия минимум из восьми кадров с
промежутками не более двух секунд. Редкие снимки анализируются отдельно.
Их оценки предназначены для карточки камеры. Для городского индекса и
оповещений используются пригодные независимые свидетельства. Уверенность
вычисляется эвристически и не измерена на размеченных наблюдениях.

### Как улучшать и проверять распознавание

- **Снег на земле.** Карточка показывает оценку модели `/v2/scene` для
  свежего кадра, если поверхность видна. Для проверки пригодны размеченные
  зоны земли и дороги с примерами асфальта, разметки, снежного покрова и бликов.
- **Снегопад.** Одиночный JPEG даёт предварительный признак. Цветовой фильтр
  отсекает сильно насыщенные точки. Для оценки начала на частом видеоряде
  нужны размеченные эпизоды со снегом, дождём, фарами и движением камеры.
  Сравнивать долю обнаруженных эпизодов, ложные сигналы в сутки и задержку.
- **Обледенение.** Для верификации нужен эталон состояния покрытия, например
  датчик состояния дороги с температурой поверхности. Видимые блики
  встречаются и на мокром асфальте. [Рекомендации FHWA по дорожным датчикам](https://ops-dr.fhwa.dot.gov/weather/mitigating_impacts/interactive_ess.htm)
- **Уверенность.** Для JPEG учитывается резкость. После сбора разметки
  сравнивать баллы с фактической долей правильных ответов на отложенных камерах
  и погодных эпизодах, отдельно для JPEG и видео. [Методика оценки калибровки](https://proceedings.mlr.press/v70/guo17a.html)

## Срочные сигналы начала снегопада

Первое пригодное свидетельство немедленно открывает эпизод early. Слабое
движение требует score ≥0.2, пространственного покрытия ≥0.4 и временной
устойчивости ≥0.6. Для confirmed нужны три различные сильные положительные
версии (score ≥0.5), либо три пригодных положительных ответа Weather VLM.
Неизвестное состояние прерывает последовательность подтверждения. Три ясных
отрицательных наблюдения завершают эпизод. Сбой связи сохраняет эпизод и
помечает старое свидетельство. Пороги требуют проверки на размеченных данных.

Повтор frame_version из последних 32 обработанных версий не подтверждает
событие и не завершает его. Это защищает также от зацикленной серии. SQLite-транзакция
сохраняет состояние детектора и журнал вместе. Принятие оператором хранится
отдельно, переживает перезапуск и повторный запрос. Демо явно маркируется и
скрыто в оперативном журнале по умолчанию. Первый открытый клиентский журнал
не вызывает поток уведомлений по старым событиям.

API — GET /api/alerts, POST /api/alerts/{id}/acknowledge, GET /api/monitoring.
Текущий SSE-поток передаёт отдельное событие alerts. Проверка очереди идёт
раз в секунду, резервная клиентская проверка журнала — раз в десять секунд.
Системные уведомления включаются пользователем. Для доставки требуется
работающий браузер с открытой вкладкой и разрешением Notifications.
Внешний канал email/SMS в этой конфигурации не настроен.

Для HLS используется восемь кадров 2 FPS через одно соединение FFmpeg.
live_start_index=-1 выбирает последний доступный сегмент живого потока.
После успешной видеосерии пауза не более двух секунд (настраивается
через hls_burst_pause_seconds, минимум 0.5 с). При сбоях действует backoff. У JPEG сохраняется
30 секунд. Источники РАН сохраняют 1800 секунд и snapshot_only. Срок появления
реального сигнала складывается из задержки оператора, интервала получения,
длительности анализа и доставки. Опубликованной гарантии задержки нет. pipeline_delay_seconds измеряет время
от начала запроса до записи сигнала. Задержка публикации у оператора в эту
метрику не входит. source_timestamp хранится отдельно, если источник его отдаёт.

Опциональный SCENE_MODEL_URL в .env подключает /v2/scene общего Weather VLM.
По умолчанию адрес пуст. Используются только новые городские JPEG-кадры,
для которых нет пригодного CV-score. Ответ проверяется Pydantic, требуется
format_valid и пригодный обзор воздуха. Ответ модели хранится отдельно от
численной CV-оценки. Расхождение методов оставляет ранний сигнал для проверки.
При ошибке модели сохраняются кадр и диагностическая причина. Для включения
укажите разрешённый endpoint и пересоздайте контейнер через docker compose.

### Серверная доставка

ALERT_WEBHOOK_URL и необязательный ALERT_WEBHOOK_TOKEN включают отдельный
серверный worker. Он работает при закрытой вкладке. Отправляется JSON эпизода
и заголовок Idempotency-Key=event_id:stage. Получатель обязан устранять повторы:
доставка at-least-once, после таймаута ответ мог быть уже принят получателем.
Bearer-токен передаётся только в заголовке, храните его в игнорируемом .env.
Используйте HTTPS для внешнего получателя. Секреты в URL не поддерживаются.

События early и confirmed записываются в SQLite-очередь той же транзакцией,
что и эпизод. Проверка очереди раз в секунду, timeout POST десять секунд,
до пяти попыток с backoff. После 120 секунд, принятия оператором или завершения
эпизода новые попытки подавляются. Подтверждение заменяет ещё не доставленный
ранний сигнал, чтобы запоздавшая ранняя стадия не пришла после подтверждения. Тренировочные сигналы наружу не отправляются.
Очередь переживает перезапуск. Статусы pending/delivered/failed/suppressed
доступны в поле delivery API журнала. Delivered означает HTTP 2xx от получателя,
прочтение сообщения заказчиком этим не подтверждается. При пустом URL доставка
выключена, устаревшие события при позднем включении не отправляются.

Для подключения пилотной камеры добавьте её поток и координаты в
`cameras.json`, проверьте городской участок в поле зрения и укажите
`"city_observation": true` и `"alert_delivery": true`. Для HLS используйте
`"type": "hls"`. Разрешайте доставку после проверки свежего видеоряда.
Камеры без разрешения доступны в локальном журнале. Отзыв разрешения
подавляет оставшиеся в очереди отправки после перезапуска сервиса.
Ранее подтверждённый эпизод сохраняет стадию до завершения.

Укажите адрес согласованного получателя в `ALERT_WEBHOOK_URL` в локальном
`.env`. Из этой папки пересоберите и запустите Compose с корневым `.env`:

```sh
docker compose --env-file ../../../.env -p snowvision up --build -d --wait
```

`/api/monitoring` показывает наличие webhook, число разрешённых камер
(`delivery_cameras`) и число камер со свежими пригодными наблюдениями
(`delivery_cameras_ready`). Успешную пробную отправку проверяйте на тестовом
получателе по ключу идемпотентности и статусу `delivered` в журнале.


## Надёжное обновление кадров

JPEG загружаются с Cache-Control/Pragma и уникальным параметром `_sv`,
с сохранением остальных query-параметров. Для подписанных URL отключите
`cache_bust` в конфигурации камеры. При сетевой ошибке, временном HTTP-сбое
или повреждённом JPEG выполняется одна повторная попытка. Общий предел —
22 секунды, размер потока ограничен 20 МиБ. Некорректный ответ не заменяет
последний хороший кадр. Отпечаток вычисляется по исходным пикселям до resize.
Повтор идентичных пикселей не обновляет возраст кадра. HTTP-успех и свежесть
кадра — разные состояния. API показывает frame_age_seconds, unchanged_since,
freshness_reason, download_attempts и http_cache_age.

В браузере неудачная загрузка повторяется без ожидания новой версии снимка.
Таймаут 12 секунд распространяется и на зависшее декодирование; слот очереди
освобождается. Backoff до 30 секунд, максимум четыре одновременные загрузки,
при уходе карточки из видимой области попытки отменяются. Предыдущий кадр
сохраняется. Одинаковые кадры у источника маркируются отдельным сообщением.
Автообновление должно быть включено для фоновых повторных попыток браузера.

Для разовой сетевой диагностики: `docker compose run --name snowvision-source-audit
--no-deps snowvision python -m snowvision.cli.audit_cameras`. Результат `/tmp/camera-audit.local.json`
в контейнере. Две выборки не доказывают постоянное зависание камеры, особенно
для источников с периодом 1800 секунд. Отчёт не коммитится.

## Ключ и текущие данные Яндекс Погоды

Укажите `X-Yandex-Weather-Key` в игнорируемом корневом `.env`. Без ключа
поле `forecast` в API имеет статус `disabled`. При HTTP 401, 403 или 429
следующая попытка выполняется через час. При сбое последний ответ остаётся
в памяти до истечения интервалов.

Текущее наблюдение также доступно в `/api/monitoring`. Панель подсказывает
проверить тип осадков по кадру при расхождении с актуальным сигналом камеры
в пределах километра от опорной точки. Стадию сигнала определяют свидетельства
камеры. Внешний webhook доставляет сигнал камеры с его источником.

## Официальные штормовые предупреждения

Сервис раз в 10 минут получает строку Камчатского края из бюллетеня
Росгидромета по ДФО. Поле `warnings` в `/api/city/outlook` содержит статус
загрузки, источник, время получения и тексты сообщений. Панель отмечает,
если в тексте упомянут Петропавловск-Камчатский, и сворачивает сообщения за
прошедшие даты. Даты извлекаются из текста и группируются по дню Камчатки.
Точный срок действия проверяется по оригиналу. При сетевом сбое панель
помечает сохранённый бюллетень. Сервер повторяет запрос через минуту.
Ссылки на источники доступны и при сбое городского API.

- Камчатское УГМС публикует местные предупреждения и уточнённый прогноз для
  Петропавловска-Камчатского. [Камчатское УГМС](https://kammeteo.ru/)
- Бюллетень Росгидромета по ДФО содержит строку «Камчатский край». Бюллетень
  может содержать предупреждения за уже прошедшие даты.
  [Экстренная информация Росгидромета](https://dfo.meteorf.gov.ru/ekstrennaya-informatsiya/)
- Карта Гидрометцентра даёт региональный обзор на 0–24 и 24–48 часов.
  Категория «Снег/Обледенение» объединяет несколько явлений.
  [Карта предупреждений ДФО](https://meteoinfo.ru/hdmapsmeteoalarmdv)
- Ежедневные прогнозы МЧС содержат сведения о рисках и ссылаются на выпуски
  УГМС. При автоматическом сборе эти ссылки пригодятся для исключения
  повторных уведомлений об одном событии.
  [Пример бюллетеня МЧС](https://41.mchs.gov.ru/deyatelnost/press-centr/operativnaya-informaciya/prognozy/5846314)

Кандидат для машинного приёма — данные системы «Метеопредупреждения» для
юга Камчатского края. В информере доступен выбор этой зоны. Публичный
машинный поток для неё пока не подтверждён.
[Информер Гидрометцентра](https://meteoinfo.ru/informer-meteoalert)
