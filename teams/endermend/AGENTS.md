# Правила работы SnowVision

## Контекст задачи

Прочитать `context/START_HERE.md`, `CURRENT.md`, `DECISIONS.md` и `RUNBOOK.md`.
По области изменений читать `BACKEND.md` или `FRONTEND.md`, для API — оба.
Активное UI/UX-задание — `context/UI_UX_PILOT_TASK.md`; план качества —
корневой `task.md`. Старые поручения и завершённые этапы не возобновлять.

Контекст хранит текущие требования, архитектуру, ограничения и проверенные
результаты с SHA. Подробную историю оставлять в Git, не копировать её в каждую
передачу. Использовать отслеживаемые Git документы как источник контекста;
`.context-local` не читать, не записывать и не использовать для передачи между
чатами. Общие правила держать здесь, команды — в RUNBOOK, сведения о слоях —
в соответствующих файлах. Для изменения применять подходящий доступный навык,
предварительно прочитав его SKILL.md.

## Постоянные требования

- Тот же проект SnowVision запускать и поддерживать на настроенном сервере.
  После изменений приложения обновлять серверную установку по
  [RUNBOOK.md](context/RUNBOOK.md), сохраняя серверные `.env` и том истории.
  Данные подключения и серверные пути — только в игнорируемом
  `context/deployment.local.env`, шаблон — `context/deployment.example.env`.
  Доступ к интерфейсу — через SSH-туннель по RUNBOOK; соединение держать открытым.
- После каждого завершённого задания готовить в итоговом ответе готовый к
  вставке промпт для следующего чата SnowVision: указывать состояние, контекст,
  что уже сделано и следующую конкретную задачу.
- Каждый файл в `teams/endermend/snowvision/backend/` — не более 300 строк.
  Если изменение превысит
  лимит, разбивать модуль или упрощать код до завершения работы.
- Для городского индекса использовать минимум `confidence >= 0.20` вместо
  прежних `0.25`. Остальные фильтры свежести, метода, географии и независимости
  зон сохраняются; порог камеры для отдельных onset-сигналов не менять.

## Выполнение и публикация

1. Проверить Git, определить результат и подходящие проверки. Сохранить
   чужие правки; включать их только по явному поручению пользователя.
2. Существенные решения и проверенные результаты записывать в отслеживаемые
   контекстные документы по их назначению (CURRENT, DECISIONS, BACKEND,
   FRONTEND или RUNBOOK). Для проверок запускать нужные команды напрямую.
3. Проверять приложение через Docker Compose. Для frontend выполнить
   `build web` с Vitest, TypeScript и Vite; при изменении backend/API —
   backend-тесты. Для документации проверить ссылки и актуальность команд.
   Не заявлять непроведённые проверки.
4. Обновить CURRENT и затронутый контекст, проверить общий diff, создать
   отдельный commit. Не коммитить секреты, БД, локальные данные или журналы.
5. Для каждой завершённой задачи, включая документацию и очистку, выполнить
   обычный push ветки `endermend` только в `fork` —
   `https://github.com/endermend/algorithms-kamchatka`. Не отправлять изменения
   в `origin` (`SHKZhenya/algorithms-kamchatka`) и не создавать PR в другой
   репозиторий. PR создавать только по прямой просьбе пользователя. Force push
   запрещён.
6. Проверить CI опубликованного SHA инструментами GitHub или официальным `gh`;
   исправить относящиеся к работе ошибки и повторно отправить коммит обычным
   push в `fork`. При внешнем блокере точно указать его результат.

Публикация в `fork/endermend` входит в завершение задачи и не требует
повторного согласования. Проверять CI инструментами GitHub или официальным
`gh`, не угадывать его состояние. После документационной задачи не выдавать
подготовленное задание за реализованный интерфейс.
