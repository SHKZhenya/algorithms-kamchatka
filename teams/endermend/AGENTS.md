# Правила работы SnowVision

## Контекст задачи

Прочитать `context/START_HERE.md`, `CURRENT.md`, `DECISIONS.md` и `RUNBOOK.md`.
По области изменений читать `BACKEND.md` или `FRONTEND.md`, для API — оба.
Активное UI/UX-задание — `context/UI_UX_PILOT_TASK.md`; план качества —
корневой `task.md`. Старые поручения и завершённые этапы не возобновлять.

Контекст хранит текущие требования, архитектуру, ограничения и проверенные
результаты с SHA. Подробную историю оставлять в Git и локальном журнале,
не копировать её в каждую передачу. Общие правила держать здесь, команды —
в RUNBOOK, сведения о слоях — в соответствующих файлах. Для изменения
применять подходящий доступный навык, предварительно прочитав его SKILL.md.

## Постоянные требования

- После каждого завершённого задания готовить в итоговом ответе готовый к
  вставке промпт для следующего чата SnowVision: указывать состояние, контекст,
  что уже сделано и следующую конкретную задачу.
- Каждый файл в `teams/endermend/snowvision/backend/` — не более 300 строк.
  Если изменение превысит
  лимит, разбивать модуль или упрощать код до завершения работы.
- Для городского индекса использовать минимум `confidence >= 0.20` вместо
  прежних `0.25`. Остальные фильтры свежести, метода, географии и независимости
  зон сохраняются; порог камеры для отдельных onset-сигналов не менять.

## Выполнение и публикация

1. Проверить Git, определить результат и подходящие проверки. Сохранить
   чужие правки; включать их только по явному поручению пользователя.
2. Существенные решения и результаты записывать через
   `python3 tools/endermend-context/context.py record "событие"`.
3. Проверять приложение через Docker Compose. Для frontend выполнить
   `build web` с Vitest, TypeScript и Vite; при изменении backend/API —
   backend-тесты и полный `context.py verify`. Для документации проверить
   ссылки, актуальность команд и тесты context hooks. Не заявлять непроведённые проверки.
4. Обновить CURRENT и затронутый контекст, проверить общий diff, создать
   отдельный commit. Не коммитить секреты, БД, локальные данные или журналы.
5. Для каждой завершённой задачи, включая документацию и очистку, выполнить
   обычный push ветки `endermend` в `fork`, обновить открытый PR этой работы
   в `SHKZhenya/algorithms-kamchatka:main` или создать новый. Force push запрещён.
6. Описание PR должно отражать весь итоговый diff: результат, выполненные
   проверки и конкретный план следующих улучшений по приоритету.
7. Дождаться CI опубликованного SHA; исправить относящиеся к работе ошибки
   и обновить тот же PR. При внешнем блокере точно указать его результат.

Публикация входит в завершение задачи и не требует повторного согласования.
Проверять PR/CI инструментами GitHub или официальным `gh`, не угадывать их
состояние. После документационной задачи не выдавать подготовленное задание
за реализованный интерфейс. Post-commit сохраняет только игнорируемый
checkpoint; не коммитить его и не запускать рекурсивные коммиты.
