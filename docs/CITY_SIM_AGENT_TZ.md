# ТЗ для Codex · Камчатка: геопространственная платформа и подключение физики

**Дата постановки:** 20.11.2026. **Владелец гипотез:** Константин (ветер, снег, геосистема; совместно с Данилом) и Константин + Денис (ночной мониторинг). **Репозиторий:** `Neverrie/algorithms-kamchatka`, рабочая ветка `codex/runnable-pilot-ci` с открытым PR №2 в `SHKZhenya/algorithms-kamchatka`.

## Инструкция агенту

Начни с `AGENTS.md` и `KNOWLEDGE_BASE.md` (если доступны в текущем рабочем каталоге), затем `weather_coverage/README.md`, `weather_coverage/geography.py`, `snowops/osm.py`, `docs/API_CONTRACT.md` и **действительного** содержимого рабочей ветки. Не считай, что `main` уже содержит PR №2. Не меняй чужие расчётные модули без необходимости. Избегай второго дорожного графа и второго погодного хранилища.

**Цель ближайшего этапа:** работающая локальная геоплатформа пилотного квартала, независимая от незавершённых расчётов Данила. Она должна показывать OSM-здания и направленные дорожные дуги, сохранять погодные сценарии и иметь заменяемый решатель ветра. Позже можно добавить 3D-рельеф, CFD, перенос снега и автоматическое ранжирование объектов.

## Уже подготовленный patch

В этом архиве находится `city_sim/` с FastAPI, OSM loader, SQLite Store, Web 3D viewer, `WindSolver` Protocol, Docker Compose, пять тестов. Не начинай тот же каркас заново: возьми его, запусти, проверь, исправь обнаруженные проблемы, аккуратно интегрируй с актуальными исходниками. Это стартовый код, **не подтверждённый готовый продукт**.

## Приоритеты P0

1. Подтверди, что `data/pkc/city.osm.gz` и `data/pkc/network.osm.gz` содержат нужные здания/дороги именно в пилотном районе. Запусти `python -m unittest discover -s city_sim/tests -v` и реальные API smoke-тесты. Если объектов нет — не подставляй фиктивные, а сформируй отчет о покрытии.
2. Добавь офлайн/локальную комплектацию веб-ресурсов для MapLibre и базовую карту/стиль. CDN может остаться как опциональный dev-вариант, но целевой Docker-тест должен работать без внешнего JS и без API-ключа. Следуй лицензиям OSM и зависимостей.
3. Добавь рельеф: проверь фактический DEM в рабочей копии; для эксперимента использовался Copernicus GLO-30. Сверь CRS, маски и смещения. DEM 30 м **не** описывает снежный нанос возле конкретного дома. Не создавай рельеф из случайных высот.
4. Проведи аудит OSM-зданий: ways, multipolygons, known height, guessed height, unknown. Не смешивай `render_height_m` с `physical_height_m`. Настрой размеры участка, границы/качество и стабильные идентификаторы.
5. Продумай производительный экспорт: при большом числе зданий не возвращай весь город одним GeoJSON; ограничься bbox и нужным уровнем детализации/тайлами. Зафиксируй один метрический CRS и единицы для расчётной сетки.
6. Соедини `weather_coverage` с редактором сценариев через адаптер, а не переписывание CSV/JSON. Раздели manual scenario, forecast и observation, храни `issue_at`, `valid_at`, исходный файл/хеш и факт интерполяции.
7. Реализуй API версий данных и сохранённых сценариев; синтетический solver используется **только в тестах**. Боевой UI должен показывать, что физический решатель ещё отсутствует.

## Контракт Данила — вопросы до подключения

- Получает ли решатель геометрию здания/квартала или только шаблон здания? В каком CRS, масштабе, с каким вертикальным датумом?
- Возвращаются только `pressure_pa` или также `u/v/w` в м/с, кинетическая энергия турбулентности/другие параметры? На каких высотах?
- Как задаются направление **ОТКУДА** дует ветер, скорость, порывы, граничные условия? Каковы расчётная область и влияние соседних зданий?
- Сетка регулярная или неструктурированная? Какое разрешение, origin, axis order, mask, nodata, границы тайлов?
- Каковы `solver_version`, `scenario_id`, `geometry_hash`, детерминизм, время и память на 1 здание/квартал?
- Вычисляет ли Данил **перенос снега** или только воздух? Если только воздух, `SnowDriftModel` будет отдельным модулем, а не визуальной интерпретацией давления.

## P1 после реального солвера

Сохранить реальный выход для двух противоположных ветров; отобразить поля на правильных координатах; затем добавить `SnowDriftModel`, который учитывает подвижный снег, склон/геометрию и условие начала переноса. На первом шаге допустим **относительный риск**, но не число сантиметров. Далее пересечь зоны с дорожными дугами через `edge_id`, зданиями/въездами и остановками, обеспечить `data_provenance`, `uncertainty` и `reason`. Каждый вывод — `physical_estimate`, `scenario_estimate` либо `observation`.

## P2 продукт

Сигнал «в ближайшие часы возможна опасная ситуация на участке X» должен передаваться в модуль мониторинга Константина и Дениса. Сравнить с простым порогом по ветру/осадкам и независимыми фото/наблюдениями. Риски должны влиять на **какое действие предлагается ответственному**: проверить, уточнить данные, подготовить технику. Не автоматизировать отправку чиновникам без согласования регламента и допустимых ложных тревог.

## Критерии приёмки и запреты

- Код и данные структурированы, модуль изолирован, запуск из README, Docker Compose и CI; любой участник может воспроизвести локально.
- Не строить с нуля Unreal/Godot-клиент и не дублировать `weather_coverage`/`snowops` без причины. Выбор конкретного 3D-рендера обратим и не влияет на API/физику.
- Не отдавать интерфейс с сотнями строк CSS/JS в одном HTML. Разделённые модули и проверяемые тесты.
- Нет авторских секретов/API-ключей, фиктивных городских высот/снегопадов, имитации «настоящего CFD» и фальшивого зелёного статуса при отсутствии наблюдений.
- При ошибке модели нет значений риска; при изменении версии геометрии существующий сценарий не пересчитывать молча.
- Демонстрация: выбор пилотного квартала → настоящие здания и дороги → создание двух разных погодных сценариев → сохранение/повторное открытие → одинаковая воспроизводимая структура входов для адаптера → при подключении настоящего солвера разные рассчитанные выходы.
- Отдельно показать, **что пока не умеет**: геозону с отсутствующей высотой здания, неготовый DEM, отсутствие реального состояния снега, неизвестную метрику валидации.
