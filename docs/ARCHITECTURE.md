# Архитектура вычислительного ядра

```text
OSM snapshot -> directed multigraph + forbidden transitions
ScenarioSnapshot -> references, closures, fleet, time windows, rates
                   |
                   v
          edge-state routing (NetworkX)
                   |
                   v
      ArcSolver: B0 or route pool + HiGHS
                   |
                   v
     expanded actions -> independent validator
                   |
                   v
      cost replay -> plan JSON / GeoJSON / metrics CSV
```

`osm.py` импортирует неизменяемый снимок, `routing.py` строит граф состояний. Состояние — последнее ребро, старт — узел депо, финиш — отдельная вершина без исходящих переходов. Поэтому прибытие в депо во время маршрута не сбрасывает ограничения поворота. Параллельные рёбра сохраняются, развёрнутый путь возвращается по идентификаторам дуг. Программные поправки в снимке могут закрывать дугу или запрещать дополнительный непрерывный поворот.

Матрица всех пар не строится. Кэш путей живёт внутри объекта маршрутизации конкретного сценария, с ключом по исходному состоянию и скорости. Снимок и граф меняются только между такими объектами. Секунды на дуге округляются вверх. Маршрутный движок ищет кратчайший по времени транзит. Экономическую оценку непосредственных путей и глобальный CARP оптимум это не гарантирует.

`validation.py` читает раскрытые дуги без обращения к поиску маршрута. `economics.py` заново рассчитывает тарифные компоненты по длинам и длительности. `reporting.py` принимает нарушения покрытия в частичном плане и останавливает публикацию плана с ошибкой структурной допустимости. Время выполнения и память процесса идут в отдельный файл, поэтому экспорт плана можно сравнивать побайтно при стабильном поиске.

Стадии C–E отделяются по контрактам вывоза, событий и HTTP. Город задаётся профилем и локальным снимком. Для тиражирования потребуется отдельное задание выбора тестовых дорог и проверка второго города.
