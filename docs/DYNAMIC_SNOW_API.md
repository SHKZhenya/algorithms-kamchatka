# Динамическое состояние снега и уборка

Версия `snow-mass-fv-1`, 22 ноября 2026. Расширение существующего FastAPI.
Старая модель Данила `087118ff` и её API сохранены. Публикация и развёртывание
этого этапа не выполнялись. UI не изменён.

## Данные и физическая интерпретация

Состояние хранит рыхлый и связанный снег в **кг/м² открытой поверхности**.
Масса ячейки равна запасу × её открытой площади. Часть ячейки, занятая зданием
или водой, исключается по векторной геометрии; частично открытая ячейка не
пропадает из-за положения её центра. Полностью закрытые ячейки возвращаются
как null, а не нулевой снег. Нулевой начальный запас не подставляется вместо
неизвестного: начальный рыхлый запас обязателен. Пользователь может задавать
скаляр, полный растр и пространственные поправки patches.

Баланс после каждого процесса:

`M = M0 + осадки + граничный вход − граничный выход − вывоз − явно заданные потери`.

Ветер переносит имеющийся рыхлый снег и без осадков. Связанный запас остаётся
на месте до механической операции. Необязательное старение переводит рыхлый
запас в связанный с сохранением массы. Осадки поступают в рыхлый слой.
Плотность не нужна для баланса; высота и её диапазон рассчитываются отдельно
по задаваемой плотности и её нижней/верхней границам. Значения по умолчанию
200 [100, 400] кг/м³ — исследовательский сценарий, не измерение города.

Сальтационная ёмкость переноса использует пороговую зависимость Pomeroy–Gray:
`Q = A ρair/g · ut/u* · max(u*²−ut²,0)` [кг/(м·с)], `A=0,68 м/с`.
Порог трения, шероховатость и доступность рыхлого снега настраиваются.
Размерный коэффициент A нельзя считать безразмерным. Основание формулы и её
эмпирический характер описаны в [SnowPappus, 2024](https://gmd.copernicus.org/articles/17/1297/2024/).

Из ёмкости вычисляются потоки через грани, ограниченные запасом донора.
Каждый внутренний выход одновременно является входом соседа. Схема сохраняет
массу и неотрицательность; шаг ограничивается CFL и max_step_seconds.
Ограничение доступности `min(1, рыхлый запас/pickup_scale)` — явное сокращённое
замыкание этой реализации, не опубликованная калибровка для Камчатки.
Двухслойное представление переносимого и неподвижного снега имеет аналог в
[SnowTran-3D](https://www.cambridge.org/core/journals/journal-of-glaciology/article/simulating-complex-snow-distributions-in-windy-environments-using-snowtran3d/9D28335437B0D4732991D0137A96EDFD).

Около зданий доступен исследовательский экспоненциальный след снижения ветра
по направлению и высоте. Это **не CFD-поле** и не добавление старых коэффициентов
осаждения к физике. Неизвестная высота не выдумывается: след такого здания
учитывается только при явно заданной сценарной высоте; контур всё равно
исключает хранение снега. В coarse cell открытые части перемешиваются;
узкие преграды и проходы внутри одной ячейки не разрешены. Нужны локальные
расчёты с более мелкой сеткой и проверка чувствительности.

Суспензия, энергетическое таяние, влажность и сублимация частиц самостоятельно
не вычисляются. `explicit_loss_kg_m2_h` — заданный внешний сток с ограничением
доступной массой, а не физический прогноз сублимации. Баланс не доказывает
пространственную точность: для неё нужны измеренные масса, плотность, ветер
и фактическая уборка.

## API

Все маршруты находятся в существующем приложении; OpenAPI: `/openapi.json`.
База `/api/v1/snow-state/territories`:

| Метод и путь | Назначение |
| --- | --- |
| `POST /` | Задать начальный запас, плотность, время, источник и расчётный домен |
| `GET /{id}?grid=true&frame=N` | Текущее/историческое состояние, растр, баланс и разрешение |
| `POST /{id}/weather` | Применить непрерывный погодный интервал |
| `POST /{id}/cleaning` | Зарегистрировать уборку, в том числе будущую |
| `POST /{id}/cleaning/{event_id}/confirm` | Подтвердить факт по источнику и явно пересчитать историю |
| `POST /{id}/replay` | Воспроизвести журнал от начального состояния и сверить state_id |
| `GET /{id}/history` | Входные события, снимки после процессов и массовые последствия |
| `GET /{id}/rankings` | Оценки объектов и повторного накопления по текущему/историческому состоянию |

`rankings` принимает `bbox`, `frame`, `kind`, `object_id`, `threshold_cm`,
`limit`, `offset`. Поддержан весь bbox города, прежнее ограничение 0,08°
для сценариев внешнего ветрового решателя на эти маршруты не распространяется.
Рейтинг отсортирован по вычисленному P90 массы. Значимость и качество не
смешиваются с массой; возвращаются отдельными полями. Высота порога зависит
от сценарной плотности и не является нормативом уборки.

`physical` содержит среднее/P90/максимум массы, глубину и её диапазон по
плотности, геометрию поддержки и покрытие. Исходная геометрия отделена от
поддержки на открытой земле: `original_geometry_measure`,
`excluded_non_ground_or_outside_domain`, `coverage_original_geometry_fraction`.
Покрытие только открытой части нельзя выдавать за покрытие всего исходного объекта.
`reaccumulated_p90_kg_m2` сравнивает состояние с **завершённой** последней
очисткой соответствующих ячеек, уже после формирования вала. Где очистки
не было, результат неизвестен. Накопление после очистки может быть вызвано
ветром, снегопадом или следующей механической операцией; причина устанавливается
по журналу, а не по одному статусу.

## Пример последовательности

Начальное состояние:

```json
{
  "bounds": [158.6554, 52.9935, 158.6614, 52.9975],
  "rows": 128, "cols": 128,
  "valid_at": "2026-01-01T00:00:00Z",
  "loose_kg_m2": 10, "bound_kg_m2": 0,
  "density_kg_m3": 200, "density_min_kg_m3": 100, "density_max_kg_m3": 400,
  "source": "Явно заданный исследовательский сценарий",
  "confirmation": "scenario", "city_geometry": true,
  "parameters": {"boundary": "closed"}
}
```

Погода после него:

```json
{
  "event_id": "weather-001", "kind": "weather",
  "start_at": "2026-01-01T00:00:00Z", "end_at": "2026-01-01T01:00:00Z",
  "wind_speed_m_s": 12, "wind_from_deg": 270,
  "snowfall_kg_m2_h": 2,
  "source": "Источник погодного входа с его идентификатором",
  "shelter": true, "unknown_building_height_m": 9
}
```

В примере 9 м — введённая пользователем сценарная высота, не факт о зданиях.
Фактическое разрешение погоды задаётся отдельно в `source_resolution_m`,
время получения — `retrieved_at`; неизвестные значения не реконструируются.
`source_coordinates` позволяет сохранить исходную точку. Ручной вход не
выдаётся за прогноз. Метеорологический угол означает направление **откуда**.

Для уборки задайте `kind=cleaning`, `event_id`, `valid_at`, `operation`,
`source`, `confirmation`. Поддержаны road_plow, sidewalk_clear, snowbank,
load_export, manual_clear, repeat_clear. Геометрия — Polygon/MultiPolygon
в WGS84 либо направленная LineString `service_line` с **явной** `width_m`.
Направление координат линии задаёт движение техники. Вал задаётся отдельной
`destination` либо `bank_side=left/right` и явной `bank_width_m`. Разворот линии
меняет сторону вала. Неизвестная ширина не подставляется автоматически.
Сохранены `related_object_ids`, исходная/целевая геометрии и объекты, чьи
области пересекаются с валом. Это сценарное последствие, не наблюдаемый факт.

`fraction`, `residual_kg_m2`, `bank_mobile_fraction` задают воздействие операции.
Не вывезенная масса обязана попасть в непустую открытую область назначения;
если это невозможно, операция отклоняется атомарно. load_export вывозит
снятую массу; у других операций вывоз задаётся `export_fraction`.
После операции запас становится начальным для следующего погодного шага.

## Время, повторы и подтверждения

Погодные интервалы должны начинаться в текущий момент и непрерывно покрывать
историю от initial valid_at. Пробелы не заполняются воображаемой погодой,
перекрытия отклоняются. Будущая уборка остаётся pending_future; погодный
интервал разделяется на её точном времени. Неподтверждённые события не меняют
снег и даже не вводят дополнительные численные шаги. GPS-прохождение следует
передавать как `confirmation=unconfirmed`. Факт/сценарий операции — отдельный выбор.

Повтор event_id с тем же содержимым возвращает deduplicated без изменения
состояния. Другое содержимое с тем же ID — 409. `expected_revision` защищает
от конкурирующего обновления. Транзакция SQLite включает журнал и состояние;
ошибка не оставляет частично обработанного события. Поздняя уборка требует
`allow_replay=true`; подтверждение прошлого события — явная операция со
своим источником и пересчётом. Это реконструкция истории, не незаметная правка.
При изменении геоданных старое состояние требует новой территории/миграции.
Каждая запись хранит источник и статус. Работа не зависит от API чужого планировщика.

## Входы и связи

Новые маршруты реестра:

- `GET /api/v1/registry/entrance-candidates`: отдельные гипотезы по окончаниям пеших линий и service-проездов.
- `GET /api/v1/registry/relationships`: дорога/проезд/подход/вход/остановка по общим OSM узлам; гипотезы отдельно.
- `GET/POST /api/v1/registry/entrance-reviews`: отклонение либо подтверждение гипотезы.

Подтверждение требует источника, **сообщённых координат** и погрешности.
Предсказанная точка сохраняется отдельно; она не становится измеренной при
простом переключении статуса. Подтверждённая пользователем запись появляется
в реестре и доступна расчётным оценкам. Самостоятельной полевой верификацией
системы такое подтверждение не является. Данные OSM наружу не записываются.

## Воспроизведение

```sh
python -m unittest discover -s city_sim/tests -v
python -m unittest discover -s tests -v
python -m city_sim.reproduce_dynamic_backend --output out/dynamic-backend --city
```

Офлайн используются включённый входной OSM-снимок, прежние городские данные
и закреплённая модель Данила. Сбор источника вынесен отдельно:
`python -m city_sim.prepare_access_sources --endpoint https://overpass.kumi.systems/api/interpreter`.
Manifest сохраняет запрос, дату получения, дату базы поставщика и хеши.
Для API с готовыми результатами укажите `CITY_SIM_DB` на state.sqlite из экспорта.
Тесты не требуют сети. Обновление источника может изменить ревизию геоданных;
старые сравнения нужно воспроизводить на исходном снимке.

Для воспроизведения прежних физических полей на прежнем снимке используйте
`CITY_SIM_ACCESS_SUPPLEMENT=0 python -m city_sim.reproduce_object_backend --output out/legacy-repeat --city`.
Исходные файлы города и закреплённый движок сохранены; отключается только новый
источник входов. Новая логика реестра при этом остаётся новой версией оценщика.

Для перепроверки сохранённых результатов и экспорта доказательств:
`python -m city_sim.verify_dynamic_backend --output out/dynamic-backend`.
Официальная проверка известных OSM ID доступна флагом
`--verify-known-official` у prepare_access_sources. Она обновляет известные узлы,
но не доказывает отсутствие неизвестных новых входов вне исходного поиска.
Начальные массивы интерпретируются на регулярной сетке EPSG:32657:
строки с севера на юг, столбцы с запада на восток; metric_bounds выдаётся API.
Вход ветра относится к высоте 10 м (как в использованной формуле трения).
Параметры воздействия уборки по умолчанию исследовательские: подтверждение факта
прохода само по себе не измеряет долю снятия, рыхлость вала или остаточную массу.
